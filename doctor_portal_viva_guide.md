## 1. 💡 Portal Overview & Features

The **Doctor Portal** is a secure, role-restricted dashboard designed for registered medical practitioners. It provides real-time access to patient lists, clinical scheduling, and medication/prescription issuance.

### Core Features:
* **Doctor Profile Header:** Displays the currently logged-in doctor’s name and area of specialization dynamically retrieved from the database.
* **Chronological Appointment Scheduler:** Renders a list of all active, completed, cancelled, or missed appointments mapped to the doctor.
* **Emergency Prioritization:** Visually tags urgent/emergency bookings and pushes them to the top of the queue.
* **Restrictive Medication Issuance ("Prescribe" Action):** Allows doctors to write a prescription containing Diagnosis, Allergies, and Medication Details only on or after the scheduled date.
* **Automated Status Update:** Completing a prescription automatically updates the appointment status from **Active** to **Completed** in real-time.
* **Prescriptions History:** Houses a searchable archive of all past prescriptions authored by the doctor.

## 3. ⚙️ Underlying System Architecture

The Doctor Portal follows a **Client-Server MVC architecture** communicating asynchronously via a RESTful API:

* **Frontend:** Loads dashboard views dynamically. JavaScript `fetch()` calls request data from local server URLs.
* **Backend:** Spring Boot receives the requests, processes credentials or queries, interacts with repositories, and serializes payloads into JSON responses.
* **Database:** MongoDB stores documents in collections (`patients`, `doctors`, `appointments`, `prescriptions`, `queries`).

### Core Database Schemas Involved:

#### 1. `doctors` Collection
Stores credential and profile metadata for verification:
```json
{
  "_id": "ObjectId",
  "username": "dr_smith",
  "password": "hashed_or_plain_password",
  "email": "smith@globalhospital.com",
  "spec": "Cardiologist",
  "docFees": 500
}
```

#### 2. `appointments` Collection
Represents the clinical contract between a patient and the doctor:
```json
{
  "_id": "ObjectId",
  "pid": "P101",
  "fname": "John",
  "lname": "Doe",
  "gender": "Male",
  "email": "johndoe@gmail.com",
  "contact": "9876543210",
  "doctor": "dr_smith",
  "docFees": 500,
  "appdate": "2026-07-22",
  "apptime": "10:30",
  "userStatus": 1, 
  "doctorStatus": 1,
  "emergency": true
}
```
* **Status Key:** `0` = Cancelled, `1` = Active, `2` = Completed (Prescription Written), `3` = Missed.

#### 3. `prescriptions` Collection
Stores the clinical record generated by the doctor:

## 4. 🧠 Algorithms & Custom Data Structures

> [!IMPORTANT]
> **This is the most critical topic for Viva.** Evaluators will ask: *"Why did you write custom code instead of just writing database queries or using built-in Java sorting?"*
> **Your Answer:** *"To showcase native data-structure control, optimize processing times, and dynamically customize priority parameters (like emergency cases) without running expensive database index updates."*

### 1. Custom Min-Heap Priority Queue (`AppointmentQueue.java`)
Instead of fetching pre-sorted data or using `java.util.PriorityQueue`, the project implements a custom binary **Min-Heap** structure:
* **Storage Array:** Managed in an `ArrayList<Appointment>` heap container.
* **Heap Operations:**
  * **Insert (`O(log N)`):** Appends the appointment to the end, then sifts it up (`siftUp`) until heap-order properties are satisfied.
  * **Poll (`O(log N)`):** Retrieves and removes the root node (highest priority), replaces it with the last element, and sifts down (`siftDown`).

#### Custom Comparison Strategy (`compare` function):
The Min-Heap determines priority using the following structured logic:
1. **Emergency Priority:** If an appointment is tagged as an emergency (`isEmergency() == true`), it is automatically prioritized. If `a` is an emergency and `b` is normal, `compare(a, b)` returns `-1` (placing `a` higher).
2. **Chronological Comparison:** If both are emergencies or both are normal, the algorithm formats their date/time values into an ISO-8601 comparable string format (`yyyy-MM-ddTHH:mm`). It performs a string comparison (`dtA.compareTo(dtB)`) to sort them chronologically.

---

### 2. Automated Overdue / Missed Status Transition
To avoid manual tracking of patient absences, the backend implements a scheduling evaluation logic during data retrieval:
* **Time Evaluation:** Every time appointments are queried, the system loops through all active appointments (`status == 1`).
* **Trigger Threshold:** If the current system time exceeds the scheduled appointment date-time by **more than 50 minutes**, the system automatically changes `userStatus` and `doctorStatus` to `3` (Missed) and commits the change to MongoDB.
* **Viva Terminology:** This is an implementation of **Dynamic State Transitioning**.

## 5. 🔄 Step-by-Step Data Flow (Operating Model)

### A. Authentication & Session Initialization
1. The Doctor inputs credentials in the main portal (handled by `AuthController.java` via `POST /api/auth/doctor/login`).
2. On successful authentication, the backend returns the doctor's details (username, specialization).
3. The frontend saves this metadata inside the browser's `localStorage` (`localStorage.setItem('name', ...)`).
4. The doctor is redirected to `dashboard-doctor.html` where JavaScript reads these values and updates the UI header.

### B. Displaying Appointments
1. The JavaScript client fires a `GET` request to `${BASE_URL}/appointments/doctor/{doctorName}`.
2. The REST API (`AppointmentController.java`) queries MongoDB for matching doctor appointments.
3. The backend runs the **Missed Status Transition check** to flag overdue slots.
4. The remaining list is loaded into the **Min-Heap (`AppointmentQueue`)**.
5. The queue runs `toSortedList()` which repeatedly pulls elements via `poll()` to output an array sorted with emergency cases and dates at the front.
6. The frontend loops through this list to inject table rows.

### C. Issuing Prescriptions
1. If the appointment date is in the future, JavaScript disables the "Prescribe" button.
2. For current/past active appointments, clicking "Prescribe" opens the sliding modal container and fills the Patient ID and Name automatically.
3. Upon submitting the form, a `POST` request is sent to `/api/prescriptions/create` containing the prescription payload.
4. **Backend Validation:** The controller verifies that the doctor is not prescribing *before* the appointment date.
5. The controller saves the prescription and sets the appointment status code in MongoDB to `2` (Completed).
6. The dashboard tables reload automatically using fetch callbacks.

## 6. ❓ Common Viva Questions & Answers

### Q1. Why did you use MongoDB instead of SQL databases like MySQL?
**Answer:** MongoDB is a document-oriented NoSQL database. It stores data in JSON-like formats (BSON), which map directly to our Java model classes without complex SQL joins. It provides high scalability, flexible schema models, and fast reads, which is ideal for clinical records (prescriptions and patient details) that can contain unstructured text.

### Q2. How does the application prevent two patients from booking overlapping appointments?
**Answer:** The system implements a **Double-Collision Doctor Booking Prevention** algorithm. When booking or rescheduling, the backend queries the database for all active appointments for that doctor on that date. It parses the time into minutes and ensures there is at least a **15-minute gap** before and after the new slot. If there is a collision, it returns a `400 Bad Request` with an appropriate warning.

### Q3. How does the front-end handle session security?
**Answer:** We check the `localStorage` key `role` on DOM content load. If a user tries to access `dashboard-doctor.html` without their role being set to `doctor`, the script intercepts and forces a redirect to `index.html`. Clicking logout clears the local storage session data.

### Q4. Describe the sift-up and sift-down mechanics of your Min-Heap.
**Answer:**
* **Sift-Up:** When inserting a new element at the bottom-right of the binary heap, we compare it with its parent node at `(index - 1) / 2`. If the child has a higher priority (i.e. is an emergency or is chronologically earlier), they swap. This repeats until the parent is higher priority or the root is reached.
* **Sift-Down:** When polling, we remove the root and place the last element there. To restore heap properties, we compare the new root with its children at `2 * index + 1` and `2 * index + 2`. It swaps with the higher-priority child. This continues recursively until heap properties are met.

### Q5. What is the benefit of serving the frontend over an HTTP server instead of just opening index.html files directly?
**Answer:** Opening files directly via `file://` causes CORS (Cross-Origin Resource Sharing) policy violations in modern browsers. Browsers restrict scripting requests to a different protocol/host. Running python's `http.server` or `npx serve` runs the files under `http://localhost:3000`, matching network communication protocols and allowing secure AJAX `fetch()` API calls to `http://localhost:8080`.
